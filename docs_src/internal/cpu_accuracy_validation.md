# CPU精度検証の入口

普段の改修では44万点を繰り返さず、難例を中心にした固定の小さな集合を使う。
未知の不具合を探す広域サンプルも残し、大きなアルゴリズム変更を採用する前に全点を確認する。
既存の測定結果・参照値・履歴はそのまま保持する。

## 検証集合と使うタイミング

| 集合 | 点数 | 用途 |
| --- | ---: | --- |
| `difficult` | 760 | 過去の不具合、現行の参照値との差、その近傍を確認 |
| `survey` | 384 | 質量比・レンズ間隔・光源半径と両計算経路を広く確認 |
| `compact`（既定） | **1,144** | `difficult` と `survey`。普段の改修に使う |
| `holdout` | 512 | 改修案を選んだ後に確認。上の集合とはレンズ条件を分ける |
| `full` | 443,700 | 追跡・支持領域・根探索・経路選択などを変更した後、採用前に監査 |

いずれも Uniform（`u=0`）と linear LD（`u=0.5`）を別々に計算する。
`compact` は元のグリッドの約0.26%であり、点数は約388分の1になる。
コンパイル時間まで同じ比率で短くなるという意味ではない。

`survey` は29種類の質量比、25種類の間隔、17種類の半径と、Cartesian / theta-first の
両経路を含む。全パラメータの直積を網羅する集合ではない。
`holdout` の32条件は `difficult` / `survey` の条件と重複しない。
既知の難例を含む条件を除いた残りから選んだ補助集合であり、未知の入力分布からの独立な標本ではない。
選択は固定して再現可能にし、同じholdoutに合わせて改修を繰り返さない。

これらは既存のcaustic付近を重点的に調べたグリッドからの抽出である。
実際の観測軌道の入力分布や、独立に新しく作った物理領域のサンプルではなく、
この集合での件数から一般的な失敗率を推定しない。

## 実行

リポジトリのルートで、microJAXの依存関係が入ったPython環境を使う。
縮小検証には、無視対象の `benchmark_cpu/` データやVBMicrolensingのインストールは不要。
入力はGit管理対象の `tests/data/cpu_accuracy/` に保存している。

```sh
# 普段の確認。既存結果を上書きしないよう、実行ごとに新しい出力先を指定する。
python tools/cpu_accuracy.py --output-dir results/cpu-accuracy/compact-01

# 改修案を選んだ後の確認。
python tools/cpu_accuracy.py --suite holdout --output-dir results/cpu-accuracy/holdout-01

# 保存済みの過去の不具合を縮小集合が拾えるか確認。数値計算はしない。
python tools/cpu_accuracy.py --replay --output-dir results/cpu-accuracy/history-01

# 大きな数値アルゴリズム変更の採用前。ローカルの全点参照データが必要。
python tools/cpu_accuracy.py --suite full --batch 36 --output-dir results/cpu-accuracy/full-01
```

`--suite difficult` / `--suite survey` で個別にも実行できる。
`--max-points 16` は起動確認用であり、完全な検証の代わりにはならない。
出力の `partial_run` に部分実行であることを記録する。

各出力先の `summary.json` にプロファイル別・集合別の結果、入力とソースのハッシュを保存する。
`points.csv` は点ごとの値・参照差・baseline差・状態・判定を含む。
実行中にソースや入力が変わった場合は成功としない。
CPUのfull finite-source計算を検査し、公開APIのmultipole近似による短絡は含めない。
実行時間にはコンパイルも含むため、速度ベンチマークとしては使わない。
元の測定と同じく、光源半径・レンズ条件を共有する光源位置をまとめて呼び出す。
既定は2点ずつで、端数は重複する位置で埋め、集計から除く。
重複を含む実評価数も出力に記録する。

## 判定と参照値の扱い

`regression_gate_passed=true` は「この集合で新たな回帰を検出しなかった」という意味である。
全点が0.1%以内で正しい、という精度保証ではない。

- 非有限・非正値の出力は失敗とする。
- 比較可能な保存参照値に対し、baselineでは0.1%以内だった点が0.1%を超えたら失敗とする。
- 既に0.1%を超える点も、参照差がさらに `1e-8` を超えて増えたら失敗とする。
- 参照値が未解決・欠損の点は、精度の合格数に含めない。baselineからの相対変化が
  `1e-10` を超えたら、参照値の再確認が必要な変更として失敗とする。
- 非ゼロの `status` は診断として記録する。値の精度不合格と同一視しない。

参照値の状態は次の4種類で保存する。

| 状態 | 意味 |
| --- | --- |
| `saved` | 従来の保存参照値。今回新たに独立な精度確認をしたという意味ではない |
| `checked` | 既存の厳格な参照監査で、独立ライブラリ間の一致と許容誤差変更時の安定性を確認 |
| `unresolved` | 参照監査で決着していない。生の参照差を表示するが、精度合格とは数えない |
| `missing` | 有効な正の有限参照値がない。精度比較から除外し、件数を明示 |

元のUniformの生の参照差115点のうち、114点は `unresolved` として残す。
残るdense row **317044** は、元の参照値約2.8962が不正確で、厳格なVBM/VBBLの両方が
約31.880995に一致した点である。この1点だけ監査済みの参照値へ置き換える。
元の値・置換値・判定根拠をmanifestに保存する。
したがって、新しい集計の差の件数が元の115点より減っても、ソルバーが改善した結果ではない。

この監査では、VBMicrolensingとVBBinaryLensingを別プロセスで計算し、両者の
`Tol=RelTol=1e-9` の値が相対 `1e-5` 以内で一致すること、さらにVBBinaryLensingの
`1e-7` と `1e-9` の値が同じ基準で安定することを要求した。
115点分の元の値・厳格な設定での値・一致度・安定性は、公開する
[manifest](../../tests/data/cpu_accuracy/manifest.json) の `uniform_reference_audit` に保存している。
これは参照値を選別する有限の検査であり、数学的な誤差保証ではない。

元の全点監査ではLDの有効参照値は440,781点、欠損・非正値は2,919点で、
0.1%を超える参照差は1点だった。未解決のUniform参照値と欠損LD参照値を合格扱いにせず、
縮小検査でも同じ区別を保持する。

## 縮小集合の根拠と更新

`tools/cpu_accuracy_cases.py` が、保存済みの回帰CSVとUniformの経路・追跡・支持領域・
キャッシュ試験から、過去に新しく0.1%を超えた点を収集する。
現在の履歴には358件の失敗記録、重複を除いて301点があり、全て `difficult` に含めている。
現行の生の参照差（Uniform115点、LD1点）も含め、各難点について同じ条件の
光源位置の中から距離が近い2点を追加する。

`--replay` は、保存された却下案の値を現在の判定関数に渡し、358件を全て検出できることを確かめる。
過去の実装を再実行する検査でも、未知の不具合を全て拾えるという証明でもない。
例えば、重点検査を通った80点追跡版の不具合dense row **200150** も固定ケースに含めている。

集合を更新する際は、ローカルの元データを使って別の場所へ生成し、選択理由・履歴・参照値の変更を
確認してから `cases.csv` と `manifest.json` を一緒に更新する。

```sh
python tools/cpu_accuracy_cases.py --output /tmp/microjax-cpu-accuracy-cases
```

生成処理も標準ライブラリだけを使い、数値ソルバーは実行しない。
保存baselineと現在のソースの一致を確認するため、baselineを更新する際は対応する
保存チェックポイントも更新してから再生成する。
新たな不具合を発見したら、その点と近傍を次の固定ケースへ追加する。
通常の単体テストと微分の検査は別に維持する。値だけを調べるこのツールで代用しない。

## 作成時の確認（2026-10-29）

- 判定・参照値・履歴検査の単体テスト12件が成功。
- `compact` 1,144点、`holdout` 512点を両プロファイルで実行し、新しい回帰は0件。
  保存baselineとの差はUniformで0、LDで最大 `4.44e-16`。
- 過去の失敗値358件を現在の判定関数へ渡し、全件を検出。
- 全点モードは16点で起動・読込・出力を確認。全443,700点の再計算ではない。
- 別ディレクトリへ再生成したCSVとmanifestがバイト単位で一致。

## 任意のローカル全点データ

公開リポジトリには縮小検証用のCSVとmanifestを含める。
全点の測定データ、試作コード、図、履歴レポートは公開物に含めず、ローカルの
`benchmark_cpu/` に保持する。通常の縮小検査と履歴リプレイはこのアーカイブを必要としない。

`--suite full` には、別途保存したアーカイブ内の次の2ファイルが必要である。

- `unified_profile_20261014/joint112/values.csv`
- `unified_profile_20261014/uniform_reference_crosscheck112.csv`

既定の探索先は `benchmark_cpu/outputs` で、`--evidence-root` で別の保存先を指定できる。
fixtureを再生成する場合は、manifestの `input_sha256` に列挙された元の履歴CSVと
保存ソースのチェックポイントも必要となる。公開リポジトリだけで全点監査や再生成が
できるという意味ではない。
